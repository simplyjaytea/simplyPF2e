## Gate contract for other tools

```js
import { assertExperimentalToolAccess, experimentalToolRefusal, EXPERIMENTAL_REFUSAL } from "./experimental-tools.mjs";
```

- `assertExperimentalToolAccess()` returns nothing when allowed. Otherwise it throws an `Error` with `code` (one of `EXPERIMENTAL_REFUSAL.WRONG_SYSTEM`, `NOT_GM`, `DISABLED`), `localizeKey`, and a localized `message` ready to notify.
- `experimentalToolRefusal()` is the non-throwing form: `null` when allowed, otherwise `{ code, localizeKey }`.
- `experimentalToolsEnabled()` is true only for the exact boolean `true`. A read failure is closed.

Required use for a new tool:

1. Call the assert at every entry point, including each console-reachable public method. A UI check does not protect a public method.
2. Call it again immediately before each native document write, after any awaited generation. The GM can turn the setting off while a run waits.
3. If a draft can outlive its run (a preview awaiting a Create click, or a reroll that spends tokens), record the experimental origin on the draft and re-check at each of those actions. `GeneratorApp` does this with `#experimentalDraft`.

Any failure is reported through the notification and leaves the draft or state unchanged. No write or provider call happens after a refusal.

## Public entry contract

```js
const forge = game.modules.get("simplypf2e").api.open();
await forge.startExperimentalMonsterRequest({
  prompt: "swamp hag",   // required; trimmed and whitespace-normalized; must be a string
  level: 6,              // required; integer -1..24; strings are refused, not coerced
  intent: "generate"     // required: "generate" (one-click create) or "preview" (no write)
});
```

- Resolves `true` once a run has started and settled. Resolves `false` when refused by the gate, invalid input, busy state, a pending Character or Encounter preview, or readiness (missing provider or sources). The reason is shown as a notification, and no progress run begins.
- A pending Character or Encounter preview blocks the request before any spend, so it is never silently replaced. A pending Monster preview is replaced, as Generate already replaces it. Create or discard the other preview first.
- Gate and role are checked first, so an API caller who is not a GM, or who has the setting off, gets no state change and no provider call.
- Before the run starts, unsaved text in the form is captured with the existing form reader. The view switches to Monster and shows the Monster draft unchanged. The request's brief and level are used only for this run. The Monster draft, Character draft, and level control are not overwritten.
- Uses the current generator controls for rarity, spellcasting, equipment, loot and treasure. A selected preset's prompt is not applied, because the brief is explicit.
- The request forces the window open with `render(true)`. A closed window is re-shown.

## Chat command

Registered as `ChatLog.CHAT_COMMANDS["simplypf2e-forge"]` (see the mechanism section) with pattern `/^\s*\/forge(?=\s|$)([\s\S]*)$/i`.

- Grammar: `/forge [--preview] <brief> <level>`. A single `--preview` may sit at either end, in any letter case. The level is the final word. Any other `--` token is refused, so a misplaced option cannot turn a preview into a creation.
- Every matched line is consumed. Refused, malformed, and accepted commands are never posted to chat.
- Unrelated chat has no matching pattern and is posted unchanged.

| Situation | Result |
| --- | --- |
| Ordinary chat, including `/forgeswamp`, `/forging`, mid-sentence `/forge` | Posted unchanged. |
| Non-GM types `/forge …` in PF2e | Consumed; `SIMPLYPF2E.Experimental.GMOnly` notice; no provider call. |
| Setting off (default) | Consumed; `SIMPLYPF2E.Experimental.Disabled` notice; no state change. |
| Non-PF2e world | Command not registered; Foundry handles the line. The module stays inert. |
| Empty, flag only, or `/forge` alone | Consumed; `ForgeUsage` notice. |
| Missing or non-numeric level, `+6`, `6.5`, `six`, extra word after level | Consumed; `ForgeLevel` notice with the range. |
| Level outside -1..24 | Consumed; `ForgeLevel` notice. Not clamped. |
| Brief empty after flags, for example `/forge 6` | Consumed; `ForgeNoBrief` notice. |
| Misplaced or repeated option, for example `swamp --preview hag 6` | Consumed; `ForgeOption` notice. |
| Valid, setting on, GM | Consumed; one Monster request starts; progress card shows. |
| Valid while a run is busy | Consumed; `ForgeBusy` notice; no second provider call; the running request is untouched. |
| Valid while a Character or Encounter preview is waiting | Consumed; `ForgeResultPending` notice; no provider call; the waiting preview is kept. |
| Valid, but readiness fails (no key, missing sources) | Consumed; readiness warning from the existing generator; no provider call. |

Consumed means the chat callback returns `false`. Notices are localized; user-entered text is never echoed into a notification, so no escaping is needed for them.

## Write and reroll boundaries

- `#onCreateActor` checks the gate for experimental drafts after scaffold lookup and immediately before `_lockCreation()` and `createActor`. A refusal sets the error, shows it in the progress card, keeps the draft, and writes nothing. `rollbackActor` is never reached with an actor.
- `#onRerollLoot` checks the gate for experimental drafts before any provider call.
- Supported drafts are never marked experimental. `#resetGenerationState` and every normal Monster run clear the flag.

## Mechanism decision: `CHAT_COMMANDS` instead of the `chatMessage` hook

The execution plan named the chat hook, with an instruction to source-check it if needed. I used the command registry because the documented contract is clearer for a command.

Evidence. Sources are type declarations from `League-of-Foundry-Developers/foundry-vtt-types`, `main` branch, fetched 2026-10-17. They are not Foundry runtime source and are not pinned to v14.365:

- `src/foundry/client/applications/sidebar/tabs/chat.d.mts`:
  - Lines 66–71: `static CHAT_COMMANDS: Record<string, ChatLog.ChatCommandPattern>` is "a registry of chat commands with associated regular expression patterns and processing functions"; "Commands are matched in insertion order."
  - Lines 251, 262: `parse` returns `"invalid"` for unknown commands; `processMessage` "fires the `chatMessage` hook". The declaration gives no order between that hook and the invalid-command error.
  - Lines 357–359: `MESSAGE_PATTERNS` is "deprecated since v14 … Use `ChatLog.CHAT_COMMANDS` instead."
  - Lines 401–412: `ChatCommandCallback` returns `MaybePromise<false | void>`, and "Return `false` to prevent message creation."
  - Lines 423–440: `ParseResult` and `ChatCommandPattern` (`rgx`, `fn`, optional `mode`, `isRoll`, `isMultiline`).
- `src/foundry/client/hooks.d.mts`, lines 1148–1164: `chatMessage(chatLog, message, chatData)` receives the trimmed text; `false` prevents creation.

Why the registry: the hook would need `/forge` to reach it before Foundry's invalid-command check, and the typings do not say that. The registry is the documented extension point for commands, and its callback contract includes "prevent message creation." Module minimum is Foundry 14, so the registry is available on every supported install.

Remaining risk: this is type evidence, not runtime evidence. The first live check must confirm that a suppressed `/forge` is not posted and that unrelated chat is unchanged.

## Limitations

- The registry contract comes from type declarations and is unverified at runtime (see above).
- `/forge` is Monster-only, one creature per command. It ignores the selected preset and uses the form's current rarity, spellcasting, equipment, loot and treasure controls.
- A mid-run gate disable blocks only the write boundary and reroll. Provider spend already in progress continues until that run finishes. Cancellation is not triggered automatically.
- Console callers can reach `startExperimentalMonsterRequest`, which is intended: the gate is enforced inside it. No second, module-level `api.forge` was added.
- A refused native write logs `actor creation failed` through the existing console path before showing the refusal message. The refusal is still the surfaced reason.
- Foundry input handling and whether the chat callback receives the full text of a long single line are unverified in a live session.
