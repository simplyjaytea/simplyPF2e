## 1. Goal and v1 boundary

**Ships in v1 (behind `experimentalTools`; see §3.4):**

1. **Loot actor destination for Forge scrolls and wands.** The existing scroll and wand flows get a "Create as" choice:
   - **Items directory** is today's behavior. It stays the default and stays ungated.
   - **Loot actor** creates one pf2e `loot` actor (`lootSheetType: "Loot"`) holding the whole planned batch. It is written in a single `Actor.create`, checked with `verifyCreatedActor`, and rolled back on failure.
   - The AI call and the item build are unchanged.
2. **Treasure parcel (new Forge kind `parcel`).** The GM sets party level (1–20), party size (1–8), rarity and a theme brief. The module reads the GM Core "Party Treasure by Level" row:
   - It fills the row's **consumable slots with scrolls of real spells**. Slot levels and counts come from the table.
   - It adds the row's **party currency as published Gold Pieces**.
   - The AI only picks a spell for each module-issued slot id. It never picks a level, rank, count or price.
   - The result is always one loot actor.

**Deferred to v2, with reasons:**
- **Permanent-item slots.** Filling them needs a picker for published permanent items at exact item levels, across weapons, armor (with runes) and wondrous items. No such pipeline exists: the Forge invents wondrous items rather than picking published ones, and `selectLoot` is scoped to creatures. v1 lists the unfilled permanent slots in the preview and in the actor description, so the gap stays visible.
- **Wands as parcel items.** A wand of rank r is item level 2r+1 and is not consumed, so it belongs in permanent slots. That waits for v2.
- **Gems and art objects as currency; pp/sp splits.** GM Core counts them as currency. v1 writes Gold Pieces only, which is exact and simple.
- **Merchant mode, staves, cantrip decks, mystified items.**
- **Subtracting treasure for parties under 4.** GM Core makes it optional ("you can subtract … you might consider subtracting less"). v1 uses the four-PC row and says so.
- **AI-written container names or descriptions.** These would need an enricher-inert proof, because the loot sheet enriches the description (§2.9). v1 uses only module text plus an optional name the GM types.

**Why the parcel is in v1:** the table is now verified from a cited source (§2.10), and the arithmetic is pure and testable. The only Foundry-facing pieces are paths already used elsewhere: the pinned scroll build and the published-coin clone. Leaving out permanent items keeps all three invariants intact (no guessing, no AI numbers, no invented content).

## 3. Design

### 3.1 Data flow

**Forge scroll/wand batch, destination "Loot actor":**
1. Generate is unchanged (`#generateConsumables`).
2. Create runs `assertExperimentalToolAccess()`.
3. `buildLootActorSource({ name, level: input.level, descriptionLines, items: planned sources })` (WP2) produces `{ actor, items }`.
4. `persistedExpectedItems(items)` runs. These items are not kits, so it returns them unchanged.
5. `assertExperimentalToolAccess()` runs again, then `_lockCreation()`.
6. `Actor.create({ ...actor, items })`.
7. `verifyCreatedActor(actor, LOOT_MANIFEST, expected)`.
8. On failure before commit: `rollbackCreatedActor(actor, "loot actor")` (WP2 in `post-create.mjs`). If a survivor remains, discard the draft.
9. The completion card offers "Open Loot Actor".

**Treasure parcel:**
1. Generate runs `assertExperimentalToolAccess()`. It refuses a party level outside 1–20 before any provider call.
2. `partyTreasureForSize(level, size)` (WP1) gives the adjusted row.
3. `planParcelSlots(row)` (WP3) gives `{ slots: [{ id, itemLevel, rank }], permanent, currencyGp }`.
4. `getScrollSpellCandidates(maxSlotRank, briefKeywords, { maxRarity })` is existing code.
5. `selectParcelSpells(brief, { partyLevel, slots, candidates })` (WP4) makes one provider call and returns `{ picks: [{ slotId, spellId, candidate }] }`.
6. `assignParcelPicks(slots, picks, candidates)` (WP3) returns assignments, unfilled slots and dropped picks, with stable reason codes.
7. `stackParcelAssignments` (WP3) merges repeats into `{ candidate, rank, quantity }`.
8. Each stack is built through the extracted Forge helper: spell document, `spellConsumableRankProblem`, pinned template via `fromUuid`, `toItemData`, `buildSpellConsumable`, then the quantity is set.
9. Currency: `fromUuid(COIN_UUIDS.gp)` → `toItemData` → `coinItemSource(data, "gp", currencyGp)` (WP2). If the coin is unavailable, the currency line is dropped with a preview warning, never replaced with a custom treasure item.
10. The preview shows slots, unfilled slots, the permanent items not included, currency, built value and table total.
11. Create follows the same loot-actor path as above.

### 3.3 Invariants

1. **No Rule Elements.** Loot actors never host them (`canHostRuleElements` is false and `rules = []`). Every cloned template and coin has `rules: []`. `buildLootActorSource` throws if any item has non-empty `system.rules`.
2. **The AI emits no numbers.** It returns `{ slot, spellId }` strings only. The module supplies slot ranks, quantities, currency, the container level and every price.
3. **Fail closed.** Unknown slot or spell ids, duplicate slots and ranks above the slot are dropped with stable codes and shown in the preview. Unfilled slots stay unfilled. A non-physical item type throws. A missing coin drops the currency with a warning.
4. **Escaping.** The actor description is localized module text, escaped and enricher-free. The container name is GM text: it is trimmed, capped at 100 characters, written as the plain `name` field, and escaped wherever the module renders it (`esc` in notifications; Handlebars `{{ }}`).
5. **Commit and rollback.** There is one native write. A post-commit presentation failure never re-enables Create.

### 3.4 Gate: put loot actors behind `experimentalTools`

**Arguments for the gate:**
- The module has never written a `loot` actor.
- Nothing from v0.3.5.73 on has been installed.
- Every merge auto-publishes to all installs.
- The hazard actor, the module's other new actor type, shipped gated, and that set the precedent.

**Arguments against:**
- Loot actors are inert: no rules, physical items only.
- The Forge core flows, scrolls and wands included, are ungated.

**Recommendation:** gate both the loot destination and the parcel kind until ledger row N12 passes. Today's "Items directory" path stays ungated and unchanged. The gate is checked at the UI tile and control, at generate entry for the parcel, and at Create entry and immediately before `Actor.create`. A closed gate at Create refuses and keeps the draft; the destination never silently falls back to "Items directory". The user can overrule this (§6).
